# Безопасность и данные

[← README](../README.md) · [Архитектура](ARCHITECTURE.md) · [Деплой](DEPLOYMENT.md)

Приложение предназначено для небольшой базы материалов. В нём есть защитные меры, но оно не является готовой системой авторизации и защиты API-бюджета для публичного SaaS.

## API-ключи

KIRO_API_KEY и QDRANT_API_KEY находятся только на сервере. SESSION_SECRET подписывает cookie. `.env` исключён из Git и Docker build context. Не публикуйте ключи в issues, логах, screenshots и чатах. При утечке отзовите ключ у провайдера и создайте новый.

При стандартном Kiro endpoint старый OPENAI_API_KEY не используется: ключ другого провайдера не отправляется в api.xkiro.com автоматически. Для production используйте HTTPS и COOKIE_SECURE=true.

## Какие данные куда попадают

| Данные | Где обрабатываются или хранятся |
| :--- | :--- |
| PDF/TXT или содержимое URL | Извлечение и разбиение на сервере приложения |
| Исходный бинарный файл | Обрабатывается временно, постоянно не хранится |
| Извлечённый текст, sparse-векторы, метаданные | Qdrant |
| Вопрос и найденные фрагменты | Отправляются в Kiro для генерации |
| Утверждения и цитаты | Отправляются в Kiro для проверки |
| История чата | DOM текущей вкладки, не сохраняется в базе |
| Сессия | Подписанная HttpOnly cookie браузера |

Нейросетевой провайдер эмбеддингов не используется. Перед загрузкой конфиденциальных материалов проверьте политики Qdrant и Kiro. Очистка базы удаляет точки текущего workspace из Qdrant, но не означает удаление уже переданных данных из систем внешнего провайдера или его резервных копий.

## Изоляция сессий

Workspace генерируется сервером и подписывается HMAC. Cookie имеет HttpOnly и SameSite=Strict. Чтение, поиск и удаление Qdrant фильтруются по workspace. Пользователь не задаёт его через JSON.

Это не аккаунты: разные браузеры видят разные базы, очистка cookie лишает доступа к прежней базе, а украденная cookie позволяет получить доступ к соответствующим материалам. Смена SESSION_SECRET инвалидирует все прежние сессии. Автоматического удаления бесхозных данных нет.

## Запросы и импорт URL

Изменяющие HTTP-запросы требуют X-Requested-With: DocumentRAG. При наличии Origin проверяется его соответствие Host. CORS для сторонних сайтов не включён. Размер тела проверяется до multipart-разбора, в том числе при chunked передаче.

URL разрешает HTTP/HTTPS, публичные IP и порты 80/443. Приватные, локальные, служебные и multicast адреса запрещены. После DNS-проверки соединение закрепляется за проверенным IP, HTTPS проверяет имя сервера, каждый redirect проверяется заново. Количество redirects и размер ответа ограничены. Эти меры уменьшают риск SSRF, но не заменяют сетевую изоляцию сервера.

## Ответы модели и интерфейс

Evidence передаётся как недоверенный текст, а модель инструктируется не исполнять его инструкции. JSON строго разбирается, ID источника и наличие цитаты проверяются кодом. Дополнительная модель-проверяющий оценивает обоснованность, но может ошибаться. Полной защиты от prompt injection и галлюцинаций не заявляется.

Пользовательские названия, вопросы, ответы и цитаты вставляются через textContent, не через HTML. Ссылки источников ограничены HTTP/HTTPS. Ответы приложения содержат CSP и X-Content-Type-Options.

## Ресурсы и публичный доступ

Встроенный ограничитель допускает 20 операций в минуту на сессию и 120 на процесс. Новый cookie позволяет обойти индивидуальную квоту. Импорт сериализован; приложение рассчитано на один worker. Для публичного проекта необходимы авторизация, квоты по аккаунтам, распределённый limiter и мониторинг API-расходов.

Локальный Docker запускается не от root, Qdrant не публикует порт на хост. В Compose у приложения read-only filesystem, ограниченный tmpfs и отключённые capabilities. Эти ограничения Compose не применяются автоматически при отдельном Docker-деплое на Render. Хранилище Qdrant содержит текст документов: доступ к нему, backups и шифрование должны контролироваться инфраструктурой.
